## Propósito

Juegos permite publicar, descubrir y jugar juegos 2D y 3D creados con la aplicación
anfitriona o importados desde herramientas compatibles. También preserva el vínculo
con el proceso de creación para que una obra terminada pueda convertirse en
material de aprendizaje, reutilización y nueva creación.

La referencia “micro itch.io” describe la experiencia de publicación y juego. La
capa de proyecto vinculada al espacio de trabajo es la diferencia propia del
modelo de Comunity Hub.

## Principio central

> Jugar puede ser el final de la experiencia o el comienzo de una creación nueva.

Un juego no se reduce a una página, una descarga ni un build cerrado. Es una unidad
con una experiencia ejecutable y un proyecto relacionado que conserva materiales,
código, contexto y linaje.

## Las dos caras del juego

La experiencia jugable y el proyecto asociado forman parte del modelo confirmado.

### Experiencia jugable

La superficie inicial está pensada para quien quiere jugar. Debe permitir:

- entender rápidamente qué ofrece el juego;
- abrirlo y jugarlo;
- conocer a su creador;
- ver compatibilidad, versión y señales de confianza;
- guardarlo, compartirlo y encontrar obras relacionadas.

La interfaz no debe exigir conocimientos de desarrollo para disfrutar el juego.

### Proyecto asociado

Desde el mismo juego debe existir un camino claro para:

- inspeccionar el código;
- explorar los assets generados o incorporados;
- entender la estructura del proyecto;
- conocer herramientas, plugins y dependencias utilizadas;
- abrir el proyecto en el espacio de trabajo de la aplicación anfitriona;
- crear un fork o remix;
- integrar código, sistemas o assets en una idea propia;
- expandir el juego y publicar un derivado.

La transición conserva el contexto: el usuario no debería tener que reconstruir
manualmente qué archivos, instrucciones o dependencias produjeron la experiencia.

## Anatomía provisional de una publicación

Para soportar ambas caras, una publicación de juego podría contener:

- build jugable y versión publicada;
- snapshot portable del proyecto;
- código fuente;
- galería y manifiesto de assets;
- procedencia de cada asset y su licencia;
- plugins, skills, herramientas y dependencias;
- instrucciones necesarias para ejecutar o continuar el proyecto;
- permisos y compatibilidad;
- changelog e historial de versiones;
- creador original, colaboradores y créditos;
- relación con forks, remixes y derivados.

Esta anatomía es un modelo de trabajo. Los campos exactos se decidirán cuando se
defina publicación y licencias.

## Verbos principales

- **Jugar:** ejecutar la versión publicada.
- **Inspeccionar:** comprender materiales, código y estructura.
- **Abrir proyecto:** continuar desde el proyecto asociado en la aplicación
  anfitriona.
- **Forkear:** crear una rama independiente que preserve el origen.
- **Remixar:** transformar la obra y reconocer sus fuentes.
- **Integrar:** reutilizar partes dentro de otro proyecto.
- **Expandir:** continuar el juego y publicar una nueva versión o derivado.

## Linaje y atribución

Forks, remixes e integraciones necesitan conservar una relación visible con sus
fuentes. Esa relación permite:

- reconocer al creador original y a quienes contribuyeron;
- entender cómo evolucionó una idea;
- descubrir derivados interesantes;
- aplicar correctamente licencias y permisos;
- evitar que la reutilización borre la procedencia del trabajo.

## Acceso técnico y derechos

Todo juego publicado debe ser inspeccionable y forkeable. La publicación incluye el
proyecto, código, assets, estructura y contexto necesarios para abrirlo en la
aplicación anfitriona o exportarlo a un entorno compatible y crear una copia de
trabajo.

Ese acceso no convierte automáticamente la obra en dominio público. La licencia
define qué puede hacerse después con el fork o con sus partes. Debe expresar de
forma comprensible, como mínimo:

- si el fork puede mantenerse para aprendizaje o uso privado;
- si puede publicarse como derivado;
- si código o assets pueden integrarse en otro proyecto;
- si se permite uso comercial;
- si se permite redistribución o reventa;
- qué atribución debe conservarse.

La interfaz debe separar visiblemente dos ideas:

- **Acceso disponible:** qué materiales y acciones técnicas ofrece el juego.
- **Derechos concedidos:** qué usos autoriza su licencia.

Una acción técnicamente posible no debe presentarse como legalmente permitida cuando
la licencia la restringe.
